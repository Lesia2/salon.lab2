# Аналіз лабораторної роботи №2: шарова архітектура та доменна модель

## Що змінилося в структурі проєкту порівняно з лабораторною 1

У лабі 1 весь код лежав у пакеті `app/` пласко: `models.py` (таблиці), `schemas.py` (валідація), `routers/` (контролери з бізнес-логікою). Тепер проєкт розділений на 4 шари:

| Шар | Пакет | Що всередині |
|---|---|---|
| Domain | `app/domain/` | сутності, value objects, фабрики, доменні помилки, інтерфейси репозиторіїв (порти) |
| Application | `app/application/` | use cases: `AuthService`, `SpecialistService`, `AppointmentService` |
| Infrastructure | `app/infrastructure/` | ORM-моделі, мапери, SQLAlchemy-репозиторії, bcrypt, JWT, системний годинник |
| Presentation | `app/presentation/api/` | контролери FastAPI, DTO, мапінг доменних помилок у HTTP-статуси |

Залежності йдуть лише в один бік: `Presentation → Application → Domain ← Infrastructure`. Домен не імпортує ні SQLAlchemy, ні FastAPI, ні Pydantic. Це перевіряє окремий тест `tests/unit/test_architecture.py`, який розбирає import-и кожного файлу.

Найпомітніша зміна — шлях бізнес-правил. Наприклад, перевірка «чи вільний час» у лабі 1 була функцією `validate_slot` усередині контролера і сама робила SQL-запит. Тепер вона розкладена по шарах:

- коректність проміжку перевіряє value object `TimeRange`;
- графік і активність майстра перевіряє метод агрегату `Specialist.ensure_can_take`;
- перетин з іншими записами перевіряє доменний сервіс `BookingPolicy` через інтерфейс `AppointmentRepository`;
- контролер лише викликає `AppointmentService.book(...)`.

Модель БД і доменна модель тепер різні класи: `AppointmentORM` має поля `start_at` і `end_at`, а доменний `Appointment` має value object `time: TimeRange` і методи `cancel`, `reschedule`, `complete`. Перетворення між ними робить мапер в Infrastructure.

Доменні помилки (`DomainError` і нащадки `InvariantViolation`, `NotFound`, `Conflict`, `PermissionDenied`) нічого не знають про HTTP. Статус-коди призначає лише `presentation/api/errors.py`.

## Які переваги дало розділення на шари

**Тестування без інфраструктури.** Це головна різниця. У лабі 1 без MySQL можна було перевірити лише формат даних (32 unit-тести). Найважливіші правила (перетин записів, графік, правило «за 2 години») перевірялися лише integration-тестами. Тепер 88 unit-тестів перевіряють домен і use cases з in-memory репозиторіями і проходять приблизно за 1,5 секунди навіть із вимкненою MySQL. Integration-тести (52) лишилися для перевірки HTTP, SQL і маперів.

**Контроль над часом.** У лабі 1 код брав `datetime.now()` напряму, тому для перевірки правила «за 2 години» доводилося вставляти записи в базу з часом «через годину від зараз». Тепер час — це порт `Clock`. У тестах його замінює `FixedClock`, і перевірка зводиться до рядка `clock.current = at(9)`.

**Правила в одному місці.** Правило «змінити або скасувати можна лише booked-запис не пізніше ніж за 2 години» тепер записане один раз у `Appointment.ensure_changeable`, а не в кожному ендпоінті.

**Тонкі контролери.** Контролер тепер лише перетворює HTTP-запит у виклик use case і результат у DTO. Права доступу (адмін чи клієнт) перевіряє Application-шар, тож та сама логіка працюватиме, якщо викликати її не з HTTP.

## Які недоліки та ускладнення з'явилися

**Більше коду.** У лабі 1 було 9 файлів з кодом (~1060 рядків), тепер 19 (~1990 рядків), майже вдвічі більше. Функціональність при цьому та сама: API не змінився, усі ендпоінти й коди відповідей ті самі.

**Мапінг.** Кожна сутність тепер існує у двох видах (ORM і доменна), тож потрібні мапери. Найскладніший — для агрегату `Specialist`: при збереженні він має порівняти робочі дні в домені з рядками в таблиці `schedules` і вирішити, які оновити, додати чи видалити. У лабі 1 SQLAlchemy робив це сам.

**Складніша навігація.** Щоб зрозуміти, що відбувається при `POST /appointments`, тепер треба пройти 5–6 файлів: контролер → `AppointmentService` → `AppointmentFactory` → `BookingPolicy` → `Specialist` → репозиторій. У лабі 1 усе було в одній функції.

**Дублювання структур.** DTO в Presentation, доменні сутності й ORM-моделі мають схожі поля. Зміна поля (наприклад, нове поле в записі) зачіпає всі три місця і мапер.

## Наскільки простіше тепер змінити БД або фреймворк

**База даних.** У лабі 1 перехід на MongoDB зачепив би 8 з 10 файлів, включно з усіма контролерами. Тепер SQLAlchemy використовується лише в `app/infrastructure/db/` (4 файли). Для переходу треба написати нові реалізації трьох репозиторіїв і `UnitOfWork` і підставити їх у `presentation/api/dependencies.py`. Домен, use cases і контролери не змінюються. Що це реально працює, показують in-memory репозиторії в тестах: це вже друга реалізація тих самих інтерфейсів.

**Фреймворк.** FastAPI тепер використовується лише в Presentation-шарі і в `main.py`. Перехід, наприклад, на Flask зачепив би контролери, DTO і обробку помилок, але не домен, use cases чи роботу з БД.

## Чому обрано Rich Domain Model

Рішення описане в [ADR 0001](../adr/0001-rich-domain-model.md). Коротко: правила салону тісно пов'язані з даними конкретних об'єктів. Чи можна скасувати запис, залежить від його статусу й часу. Чи може майстер прийняти клієнта, залежить від його графіка. Тому логічно, щоб ці об'єкти самі вирішували, що з ними можна робити. В анемічній моделі ці перевірки довелося б повторювати в кожному сервісі, який змінює запис, а саме розпорошеність правил була головною проблемою лаби 1.
